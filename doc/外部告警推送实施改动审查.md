## 结论与审查口径

本次“任务”是**把一个事件推送到一个逻辑目的端的持久投递记录**，不是给某个人发短信或打电话的任务。当前实现复用现有通知规则和媒介配置，新增专用投递账本及 center worker；没有新增人员匹配、短信/电话发送、接听回调或下游通知状态查询。

当前可以支持的结论是：**已具备本地模拟闭环和部分失败恢复保护，不能视为生产协议已接通，也不能宣称告警链路所有正常场景可用。** 本轮发现静默/过滤与强序列依赖之间的正常场景阻塞；同时发现迁移失败隔离及响应数值比较缺口。既有测试通过不覆盖这些新发现。

本报告分别保留“规范审查”和“需求审查”两个维度，不把业务取舍和代码缺陷混成一个总分。优先级含义：P1 为应在扩大验收前处理的正常功能阻断；P2 为应修正或取得明确决策的失败路径/语义风险。所有建议均未实施。

**谁建任务：**规则匹配发生在运行告警引擎的 center、edge 或 standalone alert；但真正的任务 INSERT 始终由 center 完成。center 直接调用 Register；edge/alert 只用 CenterApi 提交，不能访问本地 DB。唯一键在 DB 中仲裁重复登记。

**谁发网络请求：**只有 center.Initialize 启动外推 worker。Provider.Notify 故意返回错误，普通“测试发送”也被禁用；没有在 edge 启动第二套外推 worker。这里“只有一处发送”是进程职责和 DB 领取约束，不是对暂停进程迟到恢复/人工重发作出物理上的恰好一次保证。

**复用了什么：**现有告警判断、通知静默、订阅、通知规则、过滤、恢复开关、渠道保存及权限框架。外推任务在 SendNotifyRuleMessage 内、BuildNotifyContext/本地接收人展开之前登记并返回。原有同事件的旧渠道、全局 Webhook 等路径仍可能继续执行，没有自动禁用。

**未闭合窗口：**EventQueue 是原有内存队列；EventPersist 与首次 Enqueue 不在同一事务。事件已持久化后、通知规则异步派发/任务提交前崩溃，仍可能没有推送任务。edge 重试登记不能替代持久路由 outbox。当前没有自动回放历史事件的扫描器。

## 3. “任务”的含义及人员通知边界

任务的单位是 **dispatch UUID × logical destination**。一个故障快照、一次正常重复提醒、一个恢复快照，各有自己的派发 UUID；同一派发被多规则/订阅副本重复调用，在同一目的端应得到同一任务。任务正文是一条十字段告警 JSON，不含本地用户列表；一次尝试只发一个事件，不发事件数组。

四表含义：

| 表 | 用途 | 是否面向人员 |
| --- | --- | --- |
| external_push_task | 本次事件向目的端的不可变快照、状态、次数、版本、幂等键 | 否 |
| external_push_attempt | 一次明确 HTTP 请求的开始/结束、结果和脱敏摘要 | 否 |
| external_push_stream | 一个目的端/故障轮次的跨 worker 租约 | 否 |
| external_push_operation | 人工/系统状态处置的操作者、理由和前后状态 | 否 |

| 能力 | 是否本次新增 | 核对依据 |
| --- | --- | --- |
| 规则/订阅命中与渠道配置 | 复用既有框架，增加一种 request_type | dispatch 专用分支、既有表单 |
| 外推字段映射和本地投递状态 | 是 | Payload、渠道配置、任务账本 |
| 按本地用户数建立外部请求 | 否，专用分支绕过人员参数解析 | dispatch.go:635-646；dispatch 测试故意传多个 user_ids/user_group_ids |
| 人员匹配/值班选人/通知升级 | 否 | 未改用户/排班/升级模型，worker只持有DB和事件快照 |
| 短信发送/电话拨打 | 否 | 没有新增此类Provider或供应商调用；既有短信电话代码不在本次diff |
| 电话接听/挂机回调 | 否 | 新增路由仅登记、查询、详情、人工操作 |
| 对方消息/人员通知状态查询 | 否 | worker只POST事件；Get只查本地表，没有查对方API |
| 管理员“确认已收到” | 是，但为本地人工核对记录 | Act/operation；不是接听回执或对方查单结果 |

不能把“复用平台本来已有用户、短信、电话框架”写成“本次实现了这些通知”。同一事件若还配置旧短信/电话或其他渠道，它们仍按旧逻辑执行；外部平台以后也通知时，可能出现两边同时通知，需在后续切换时明确责任，当前实现没有跨平台人员去重。

## 4. 哪些既有行为改变，哪些只是新渠道约束

| 项目 | 实际变化与限制 |
| --- | --- |
| 原 HTTP/SMTP/Script/其他 Provider 的发送、重试、成功判定 | 未改实现路径；专用分支在其前 return。新渠道不使用通用HTTP自动重试。不代表所有部署/真实供应商已回归验证。 |
| 本地接收人展开 | 原渠道不变；专用外推不调用 BuildNotifyContext/GetNotifyConfigParams，不按人数复制。但同事件旧流程仍可能调用 fillUsers，这是既有行为，不是外推新增选人。 |
| 重复提醒触发间隔、次数 | 原 NotifyRepeatStep/NotifyMaxNumber 裁决不变；每个实际入队快照有新 dispatch UUID。没有实现“一轮故障只推一次”。 |
| 外推重复策略 | 必须显式选 all_dispatches 或 review_repeats。前者每次派发各保留任务，后者把序列>1的故障放 manual；不是永久丢弃。但两者均被强前序规则进一步限制，见 R1/R2。 |
| 静默/过滤/抑制/恢复开关 | 没改既有拦截位置，也没为外推绕过开关；然而静默快照推进序号而不建任务，产生新的外推阻塞，不能概括成“行为完全无影响”。 |
| 故障/恢复关联 | 既有事件 hash/恢复检测没有重构；新增 UUID/序列辅助外推配对。所有先前 problem 序列被设为依赖，恢复复制首故障的客户、设备、首次故障时间、触发器、等级、标签。 |
| 恢复是否必须人工确认 | **不是一律人工确认。**全部前序自动 accepted 时恢复可自动发；只有前序 unknown/manual 等才阻塞。但缺序列/未发送重复也阻塞且无操作出口，是更强的新约束。 |
| 本地恢复被过滤 | 不建恢复任务，不自动补造故障/恢复；对方可能永久保留故障。是否必须同步恢复仍未决定。 |
| 事件数据/旧 Webhook JSON | 当前/历史事件新增三个无 omitempty 的JSON字段；回调若直接序列化事件会看到这些加法字段。旧请求严格拒绝未知字段的兼容性未专项测试。 |
| 事件持久化/启动 | 三个身份列是全局持久化依赖，关闭媒介也会同步尝试加列；DDL耗时/失败会影响原启动和持久化路径，见 S1。 |
| center/edge | 原事件持久化路径不变；新增 edge→center 幂等登记。只有 center 发外推请求；实际两进程部署尚未验。 |
| 默认设置 | 新建外推预设关闭；不修改 etc/或旧渠道开关。仅允许 simulation，地址、测试签名、恢复值等无可用默认值。但center即使没有启用渠道仍启动两worker并扫描新表。 |
| 普通通知记录 | 专用渠道登记成功不再写普通“发送成功”，只记task ID日志；登记失败仍写失败。推送结果查专用账本；普通“已通知事件”范围不能完整代表该渠道。旧渠道记录不变。 |
| 规则流水线改写 | drop/过滤仍生效，但外推报文重新读取原始历史事实，流水线对副本字段的改写不用于外推报文。与按通知副本渲染的旧渠道不同，需在字段映射验收时明确。 |

没有发现另行新增“所有事件必须通知到人”“故障已推就无条件补发恢复”等业务规则。**发现的额外规则**是：所有历史重复/静默序列都成为后续外推前提；同目的端全库启用配置必须同映射。文档已披露这些限制，但披露本身不等于已取得业务取舍，也不能消除正常使用场景的问题。

## 5. 两个审查维度的发现

### 5.1 规范审查（Standards）

**S1 — P2：身份列迁移失败会影响全部模块迁移，失败隔离不完整。**

models/migrate/migrate.go:284-292 新增同步 AddColumn，一旦失败直接 return；这发生在 :337 全部 dts 的 AutoMigrate 循环之前。既有 Migrate():62-66 忽略返回错误，因此既跳过本次四表，也跳过之后其他模块迁移，新增返回错误本身未在此层记录。center.go:225-228 只停新 worker，不能恢复被跳过的迁移；AlertCurEvent/AlertHisEvent 已无条件持久化新字段，缺列会使原事件 INSERT 报错。旧通知消费者对持久化失败仍可能继续发原渠道，故不能简单写成“所有旧渠道停止”，但事件持久化和升级的风险确已扩大。

建议后续明确迁移错误传播、启动失败或兼容降级策略，并补“AddColumn失败、其他迁移是否继续/告警是否启动”的故障注入。保留必要身份列，不能因为这是新渠道就忽略全局schema影响。适用依据：用户“不修改现有渠道行为”，AGENTS.md/CLAUDE.md 的跨数据库及失败路径要求。

**S2 — P2：业务 status 的比较不是精确数值判定。**

worker.go:294-305 用 json.Number→strconv.ParseFloat(64) 后比较200。合法JSON数值 200.00000000000000001 不等于200，却会舍入为200，从而在HTTP 2xx时被标 accepted。本轮离线 float64/精确十进制对照证实该舍入，不是一次新HTTP集成测试。map解码还默认保留重复 status 键的最后一个，未主动拒绝歧义报文。重复键是否额外要求拒绝可单独约定，但浮点误受理已违背精确“数字200”语义。

建议后续使用无浮点舍入的数值判断，保留数字200.0这一现有测试允许的等值写法，并补近200小数、重复键等用例；本轮不改解析器。

**判断性复杂度建议（非代码风格硬违规）：**全序列依赖与全目的端映射检查确有保守防重/保序目的，但约束比必要条件更强；固定双worker/固定租约可以保持简单，不必本阶段做通用任务引擎。无需为“字符串状态很多”另建大框架。未发现更改 plus 导出入口签名、遗漏全部SQL方言、漏配静态资源、绕过任务管理员权限或新增人员通知功能。

### 5.2 需求审查（Spec）

**R1 — P1：正常静默解除后的第一条外推可能永久等待不存在的前序。**

以 repeat_policy=all_dispatches 为例，可从代码静态构造如下路径：

1. 新故障在“只屏蔽通知”中产生，process.go:574-580 仍保存事件快照，pushEventToQueue():639-649 给它 sequence=1。
2. consume.go:127-137 先持久化后因 NotifyMuted=1 返回，不会登记该渠道任务1。
3. 静默解除，process.go:592-598 明确把首次真实通知补发；它继承轮次且 sequence=2。
4. worker.go:179-207 要求1..sequence-1每个problem都有任务且 accepted/confirmed，任务1不存在，任务2进入 waiting_predecessor。
5. store.go:180-205 既不能确认一个没有attempt的虚构任务，也没有“缺序列已被合法过滤”的关联/处置入口。刷新、等待、重启和hold均不能补齐。

已经发出故障1后，静默期间出现影子快照2，解除后重复3/恢复4同样可能卡住；临时关闭渠道或规则过滤中间重复也可形成空洞。若选 review_repeats，解除静默后的首个真实外推也会因 sequence>1 先被归为“重复提醒”而进 manual；授权发送后仍会因缺序等待。此结论为当前调用链推导，**本轮未写/运行复现测试**；现有测试没有贯穿“静默→解除→专用渠道”。用户要求沿用静默/过滤并不等于授权把被过滤事件永久设为发送障碍。

建议后续区分“全事件快照顺序”和“该目的端实际命中投递的顺序”，在不补造故障、不绕过本地开关的前提下明确合法过滤空洞如何表达；先补端到端回归，再决定改法。本轮不选择具体新业务语义。

**R2 — P2：所有重复提醒都成为恢复的硬依赖，超出了‘故障结果不明不得抢先恢复’这一最低条件。**

worker.go:179-207 对重复任务和恢复一律检查全部前序problem。review_repeats 虽“保留待业务决定”，但未发送重复不能confirm_received（要求Attempts>0），要放行恢复实际上只能把每条重复都授权发送并取得受理，或一直阻塞。没有独立“本轮不再推重复但原故障可恢复”的方案。已在实施文档写明，不属于偷偷一轮合并；仍是一项尚未约定的业务限制。

建议单独决定：恢复究竟只依赖首故障/最近一次已投递故障，还是依赖所有业务要求投递的提醒；未知真实已发故障继续阻塞原则应保留，不能直接删检查或自动跳过 unknown。

**R3 — P2（配置策略）：同一目的端全库启用规则必须使用完全相同参数。**

routes.go:26-65 扫描所有启用规则，不判断是否引用当前告警、是否过滤互斥，六个参数（包括客户、设备类型、标签及重复策略）必须全部相同。同一真实平台配置第二客户或不同设备类型，即便不会同时命中，也可使首任务 validation_failed；换 destination 则改变去重域并可能绕过同目标去重。

这能阻止异步多规则“第一条已发、第二条才发现冲突”的窗口，具有可靠性动机，且界面/文档明确提示；它仍不是完整生产多客户映射方案。建议保留模拟保护的意图，后续按同派发实际命中路由/确定性路由快照设计校验，不能仅以新增不同目的端键代替业务目标定义。本轮不删除检查。

**独立于上述发现的已披露边界：**首次任务登记前仍可丢失；老活跃事件/外部输入缺合法UUID会拒发；真实引擎进程重启、并发事件持久化与实际edge部署没有完整证据。不能把DB唯一键等同跨整个告警生命周期恰好一次。

## 7. 成功、异常、重试和人工状态的实际判定

### 7.1 请求和响应

请求在 worker.send 中明确构建，生产地址会被模型校验拒绝：

~~~text
POST <显式配置的 http://数字回环IP:端口/path>
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
body = url.Values{"json": {完整Payload对象的JSON字符串}}.Encode()
~~~

使用新的http.Transport，Proxy=nil、DisableKeepAlives=true；http.Client超时由渠道显式设为1–10000ms；CheckRedirect=ErrUseLastResponse。不复用既有通用HTTP重试。响应最多读取65537字节，超过65536或读取错误即unknown；解析必须是一个JSON对象且后面到EOF。

| 输入/阶段 | 当前结果 | 是否自动再向接收端发送 |
| --- | --- | --- |
| 本地配置/字段/身份校验失败 | validation_failed；登记可能仍返回task ID | 否 |
| 合法任务且无需等待 | pending；领取事务先保存sending+attempt | 首次发送一次 |
| HTTP 2xx + 响应完整 + 单JSON对象 + status为number且float64值等于200 | accepted（接口报告受理） | 否；S2说明数值精度缺口 |
| status字符串200、业务非200、HTTP非2xx | unknown，不能证明对方未保存 | 否 |
| 非JSON、空体、截断、尾随JSON、数组、超大响应 | unknown | 否 |
| HTTP重定向 | 不跟随；3xx归unknown | 否 |
| 超时/连接中断/取消 | unknown；可能已经保存 | 否；即使某些明确未连接错误也保守不自动重投 |
| 领取/发送后进程崩溃 | sending留在DB；到30秒租约过期变unknown并记审计 | 否，不重新领取sending |
| 接收端成功但本地结果事务失败 | 任务可能仍sending，后续到期unknown | 否；不能凭客户端已读成功保证本地已记账 |
| 任务尚未领取时通道关闭/删除 | manual，保留快照 | 否；重新启用不自动释放manual |
| 保存的规则禁用/配置变化/映射冲突 | worker校验失败或manual，原快照不自动覆盖 | 否 |

重试分两类：edge→center 的**任务登记**允许最多3轮（每轮可尝试配置的多个center地址；超时2秒，退避初始100ms），依赖唯一键幂等；center→外部的**告警POST**无自动重投。不能把“三轮登记”写成“外部报警重试三次”。

### 7.2 状态与人工操作

| 状态 | 真实含义 |
| --- | --- |
| pending | 已有本地任务，等worker校验/领取，不等于对方收到 |
| sending | attempt已持久提交，可能尚未出网、正在发送或已发送 |
| accepted | 自动响应符合当前受理判定；不证明对方后续通知 |
| confirmed_received | 管理员核对后明确确认收到；原unknown attempt不改，依据在审计 |
| validation_failed | 本地条件不成立或映射歧义；不可据此声称已投递 |
| unknown | 是否落库不明，需外部人工证据，不能自动重投 |
| waiting_predecessor | 当前强序列规则不满足，包含R1缺失任务情况 |
| manual | 显式保留、重复策略未定或渠道关闭等，需要处置 |

人工接口只接受非空理由（后端不超过1000字节）和观察到的task version，数据库CAS防双击/并发覆盖；操作者来自管理员身份。GET/刷新只查本地表，没有对外查单、发短信或自动重投的副作用。

- confirm_received：仅unknown/manual，且Attempts>0；改为confirmed_received，保留attempt原结果，可解锁已有前序依赖。
- authorize_resend：仅unknown/manual，先重新验证原快照，改回pending；仍受渠道启用/模拟地址/映射/前序检查。新尝试不新建同一派发task。
- hold：不能对sending/accepted/confirmed操作；不表示跳过前序。
- accepted/confirmed禁止重发；本地validation_failed不能直接修正快照后重发，缺失前序也无直接处置入口。
- 系统不能替管理员验证“旧worker和请求已停止”。暂停旧进程可能迟到继续执行，人工授权前必须外部核对。当前没有外部幂等key协议或fencing能力。

### 7.3 页面是否误称人员成功

当前新页面把accepted译为“接口报告受理”，confirmed_received译为“人工确认已收到”，并展示“不表示业务消息、人员通知、短信或电话完成”。人工操作成功提示是“操作已记录”。专用登记成功不写普通通知成功记录。未发现将外推标为人员/电话成功的新增文案或状态实现。

但accepted只是响应判定，**连‘对方已保存’也未在本轮真实平台验证**；对方人员通知更无证据。Task/attempt的unknown仍显示未知，人工确认没有伪造HTTP成功。

## 9. 建议及本轮处置

1. **保留**现有通知规则+专用渠道+持久任务的职责划分，以及无自动重投、明确人工审计、模拟生产隔离；没有证据支持把这些统称为“新增人员通知系统”后删除。
2. **下轮优先处理需求轴R1**，用静默首发/解除、中间重复过滤、中途启用渠道的真实规则链路补回归。先确定合法空洞与实际投递序列的表示，不能直接伪造缺失故障或绕过恢复开关。
3. **规范轴单独处理S1/S2**：迁移失败传播/隔离与精确业务状态判定；两者都不是继续添加生产功能的理由。
4. **取得R2/R3业务取舍**后再调整重复提醒/恢复依赖和多映射策略。不要默认“一轮只推一次”，也不要把每次重复都必须发送作为既定协议。
5. 生产适配、签名、真实edge部署及首次登记outbox放到明确的下一阶段；若暂不解决登记前窗口，应继续写明可能丢失，不能以“有任务表”验收可靠不丢。
6. 新一轮实施仍需单独授权与验收；本轮没有进行上述调整、重跑模拟、迁移、启用渠道、提交或回退。新增本报告不代表旧预览被刷新或公网验证通过。
