# 1.0平台推送部署与密钥操作手册

适用于 Linux 上直接运行 center 或使用 Docker Compose 部署的场景。本文件随源码提交，不含真实密码。这里只说明部署操作；阅读文档、创建文件或检查密钥状态都不会发送告警。本轮文档交付不执行部署、不启用渠道、不调用1.0接口。

## 1. 部署前准备

1. 确认发布版本包含“1.0平台推送”媒介；默认关闭。升级已有数据库会保留用户配置，不应假定已有媒介也是关闭的，操作前先检查。
2. 从业务方单独取得双方约定的签名密码，不自行生成随机密码或使用样例sign代替。已有正确密钥应沿用，不因升级重新生成。
3. 确认 center 的实际运行账号，以及启动参数 `--configs` 指向的配置目录。下面的账号 `n9e`、源码路径 `/opt/nightingale`、服务名 `n9e` 和 Compose 服务名 `nightingale` 均是示例，按部署实际值替换。
4. 准备与发布版本一致的 `scripts/external-push-key.py`（需要 Python 3.9 或以上）。若二进制安装包或镜像不含脚本，从同版本源码取得；不要把真实密钥放入源码、Git目录、安装包或镜像构建上下文。

| 内容 | 保存位置 | 是否随Git/镜像分发 |
| --- | --- | --- |
| 功能代码、默认媒介、配置示例、本手册 | 仓库 | 可以 |
| 密钥密码原文 | 客户服务器的独立文件 | 不可以，单独保管和交付 |
| 密钥引用→文件路径、数据库连接等部署参数 | center实际加载的运行配置 | 不提交真实部署配置；可以提交脱敏模板 |
| 通知媒介、通知规则、字段映射、推送任务与审计 | 客户独立数据库 | 不随代码发布，迁移需另行备份/导入 |

只有 center 读取密钥和发送请求。edge/独立alert进程通过CenterApi登记任务，不需要放置密钥。多个center均可能领取任务，每个发送节点都必须可读取同一引用对应的相同密钥；页面的一次检查只证明当前处理请求的center可用。

## 2. 密钥文件和引用规则

| 项目 | 当前规则 |
| --- | --- |
| 默认引用 | `platform10-v1`，页面填写引用，不填写路径或密码 |
| center默认读取路径 | `/etc/n9e/secrets/platform10.key` |
| 文件内容 | 密码原文的UTF-8字节，不加引号、方括号、BOM、回车、换行或NUL；非空，最多65536字节 |
| 空格 | 密码内及首尾空格原样参与计算；程序不会自动修剪，必须与业务方约定一致 |
| 推荐权限 | `0600`或`0400`，所有者为center实际运行账号；受控只读组可用`0640`或`0440` |
| 不接受的权限 | 其他用户可访问、组可写、任何执行位；`0644`及Secret常见的`0444`也会被拒绝 |
| 文件类型 | 可读普通文件；父目录需要允许服务账号遍历，建议由部署管理员或服务账号独占管理 |

签名按已确认协议计算：`MD5(UTF8(problemTime去掉普通半角空格 + 密码原文))`，结果为32位大写十六进制。文件内保存密码，不保存预先计算的MD5或某次报文的sign。完整实现见[签名说明](../api/external-push-signing.md)。

## 3. 方式一：直接运行center

### 3.1 首次创建文件

先确认默认路径没有已有密钥。下列命令仅用于首次创建，辅助工具拒绝覆盖已有文件；密码交互输入两次，不回显、不写入命令参数或shell历史。

```bash
sudo install -d -m 0700 -o n9e -g n9e /etc/n9e/secrets
sudo -u n9e python3 /opt/nightingale/scripts/external-push-key.py
sudo -u n9e test -r /etc/n9e/secrets/platform10.key
```

如果已有正确文件，跳过创建，确认权限和服务账号读取能力即可。不要用`echo`写密码，也不要用`cat`输出文件检查内容。自动化部署若使用工具的`--stdin`，输入必须来自受控密钥源，传递精确字节且不附加换行。

### 3.2 选择默认路径或自定义路径

采用默认路径及默认引用时，无需新增路径配置。若客户将文件放在其他仓库外位置，在center实际加载的配置目录中配置：

```toml
[Center.ExternalPushKeyFiles]
platform10-v1 = "/srv/n9e-private/platform10-v1.key"
```

路径必须是center所在机器可访问的绝对路径。新建该路径文件可给辅助工具传入`--path /srv/n9e-private/platform10-v1.key`；其父目录与所有者按3.1同样处理。不要照抄开发机路径或预览实例目录。

如果同一配置目录中已有`[Center.ExternalPushKeyFiles]`，编辑原表，不在另一个TOML文件中重复声明相同表或键：当前加载器会将目录里的TOML拼接解析。运行配置只记录路径，不写密码。

### 3.3 加载配置并检查

变更路径注册配置后重启center。若使用systemd，确认单元名后执行（示例）：

```bash
sudo systemctl restart n9e
sudo systemctl is-active n9e
```

若未使用systemd，通过现有进程管理方式重启，不另起一套center。仅在已有注册路径下首次补放文件，不需要重启；页面状态检查和后续任务会重新读取文件。补放文件不会自动重投已经失败的任务。

## 4. 方式二：Docker Compose

### 4.1 在宿主机单独准备文件

建议宿主机使用`/srv/n9e-private/platform10-v1.key`。从宿主机运行同版本辅助工具：

```bash
sudo install -d -m 0700 /srv/n9e-private
sudo python3 /opt/nightingale/scripts/external-push-key.py --path /srv/n9e-private/platform10-v1.key
```

首次创建的文件归执行工具的账号所有。根据镜像和Compose的实际运行UID/GID设置目录、文件的所有者，确保容器内center可读；非root容器不能直接读取宿主机root所有的`0600`文件。已有容器可用`docker compose exec -T nightingale id`核对身份，不要假定各客户镜像的UID相同。变更所有者后仍保留受限权限，不能通过改成`0644`解决读取错误。

例如已确认center的UID/GID均为1000时，设置如下；1000仅为示例，必须替换为实际值：

```bash
sudo chown 1000:1000 /srv/n9e-private /srv/n9e-private/platform10-v1.key
sudo chmod 0700 /srv/n9e-private
sudo chmod 0400 /srv/n9e-private/platform10-v1.key
```

### 4.2 只读挂载到容器默认路径

在客户现有Compose文件的center服务下合并下列挂载，保留其他配置、卷、网络和启动参数；这不是一份可独立启动的完整Compose文件。

```yaml
services:
  nightingale:
    volumes:
      - type: bind
        source: /srv/n9e-private/platform10-v1.key
        target: /etc/n9e/secrets/platform10.key
        read_only: true
        bind:
          create_host_path: false
```

先创建宿主机普通文件，再启动容器；`create_host_path: false`用于避免源文件缺失时被当成目录创建。该示例使用Docker Compose v2，部署前以实际版本执行配置检查。宿主机路径可以变化，容器内路径保持默认即可。此时不需要新增密钥路径注册配置。

若使用自定义容器内路径，`[Center.ExternalPushKeyFiles]`必须填写容器内路径，不能填写仅宿主机可见的路径。运行配置所在目录也应通过原部署方式持久保留。

### 4.3 应用挂载并验证

确认实际项目目录、Compose文件及服务名后执行：

```bash
docker compose config --quiet
docker compose up -d --no-deps nightingale
docker compose exec -T nightingale test -f /etc/n9e/secrets/platform10.key
docker compose exec -T nightingale test -r /etc/n9e/secrets/platform10.key
```

修改挂载需要重新创建容器以应用新配置，单纯`restart`不会应用新的卷配置。若只修改center已挂载的路径注册配置，重启该服务即可。不要把密钥`COPY`到镜像中。单文件bind挂载下替换宿主机文件的操作可能不更新现有容器的文件视图，轮换时使用新文件并重新创建容器，不依赖热替换旧文件。

## 5. 页面只读检查与启用顺序

1. 保持“1.0平台推送”关闭，管理员进入“告警通知→通知媒介→1.0平台推送”。
2. 确认签名方式为center密钥文件，密钥引用为`platform10-v1`（或本次明确配置的新版本引用）。
3. 点击“检查密钥状态（只读）”，应显示可用。这个检查不读取告警、不发送请求、不修改任务、不显示密码，只校验文件读取和格式；不能证明密码与1.0约定一致。
4. 核对已保存的接收地址`https://admin.ztservice.cn/messageWarn!acceptWarn.act`、POST表单字段`json`、时区、客户归属和各字段映射。正式部署不自动继承开发预览里的测试规则；不要导入`label-simulation-*`模拟媒介/规则作为生产配置。
5. 在通知规则选择该媒介，配置实际事件标签键及等级映射，再由告警规则绑定通知规则。故障次数和间隔由告警规则控制，恢复继续受本地恢复开关、屏蔽和过滤控制。
6. 业务方授权真实联调后再启用。1.0可能触发真实账号、短信及电话通知。先核对一条故障，得到确认后再核对关联恢复，不以“密钥可用”或HTTP成功代替业务验收。

任务页“1.0接口报告接收成功”表示HTTP及响应体符合受理判定，不证明人员已通知。超时、异常响应或发送中崩溃可能是结果不明，需核对后按人工操作处理，不能连续点击重发测试连通性。

## 6. 升级、迁移、备份和轮换

| 操作 | 处理步骤 |
| --- | --- |
| 同服务器升级 | 保留原数据库、运行配置、仓库外密钥及挂载。升级后逐个center检查密钥状态及渠道开关，不重新生成密码 |
| 迁移到新服务器 | 单独安全转移原密钥，重新设置所有者/权限；按新机器或容器路径配置引用，恢复数据库和运行配置后检查，不把预览库当客户正式库 |
| 多center部署 | 每个节点配置相同引用与对应的相同密钥字节；路径可以不同。逐节点检查，经过负载均衡的一次成功结果不代表所有节点可用 |
| 备份/恢复 | 数据库、路径配置、引用版本与密钥文件分别保管并保持对应。密钥备份存于受控位置；普通数据库备份不能恢复密码原文 |
| 修改密码 | 先与1.0协商，暂停渠道并核对在途任务和未恢复故障。使用新文件及新引用（例如`platform10-v2`），配置各center路径，重启后检查，再明确切换媒介引用 |

同一引用对应的密码应保持不变，不直接覆盖`platform10-v1`文件。恢复和授权重发会核对原problemTime、签名及密钥版本；中途换密码会阻止相关请求。原版本应保留至旧轮次、在途及待核对任务完成；新旧密码能否在1.0同时使用需要对方确认，不能仅因新增了`v2`文件就认为轮换完成。

升级与回退均应保持数据库、配置和密钥版本可对应。本手册不授权清空任务、自动补发历史任务或修改1.0。

## 7. 常见错误处理

| 页面/任务提示 | 核对与处理 |
| --- | --- |
| 文件不存在 | 检查路径注册、容器内路径及挂载；确认源是文件，不是目录 |
| 文件不可读/权限不安全 | 核对服务UID/GID、父目录遍历权限、文件权限；只读挂载不会替代Unix权限校验 |
| 文件格式错误 | 从约定密码重新安全配置，排除编辑器追加换行/BOM、引号及复制错误，不让程序自动修剪密码 |
| 引用未配置 | 页面引用与center注册表完全一致；自定义引用必须逐节点配置并重启 |
| 状态可用但1.0业务未出现 | 文件可读不代表密码正确或对方完成业务处理；核对请求/尝试记录及双方日志，不盲目重发 |
| 补放密钥后旧任务仍失败 | 新任务会重新检查；旧失败任务不自动排队，先查尝试次数和审计，再使用明确的人工处置流程 |

密钥文件错误不会阻止center启动，也不影响其他渠道；受影响的新任务会记录本地校验失败且不发送。已经尝试的任务无法取得原密钥时会转人工处置，不应推断对方未收到。
