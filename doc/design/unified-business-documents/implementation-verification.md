# 档案管理实施验证

日期：2026 年 10 月 23 至 25 日。基线为 main `a20cd71f`，实现位于独立 worktree 的 `feat/feature-planning`。正式页面、接口、数据库与文件存储已经接通；全量工程检查与本地浏览器场景通过，最终运行身份及公网浏览器结果随交接提供。人工验收和生产发布另行确认。

## 实现范围

正式入口为 `/archives`，沿用 main 外壳、PageLayout、EnhancedTable 和方案 A 列表。培训服务、巡检报告、故障报告、其他文档共享档案、文档、历史和日志能力，按类别保留业务字段与归档材料要求。

在线文档使用固定版本 Canvas Editor 和受保护的 Markdown 转换；复杂对象与页设置留在规范快照中。Word 转换需预览确认，保留原件并创建在线副本。PDF.js 提供阅读与批注，在线文档的阅读、PDF 导出和打印复用服务端同一份生成结果。导出 worker 为随 Go 打包的离线 CLI，不新增 Node HTTP 服务。

自动保存是个人私有草稿；正式保存产生不可变版本。数据库租约阻止同文档多窗口编辑，刷新恢复会轮换令牌和代次。档案字段使用打开表单时的 revision，历史恢复和文件替换均保留旧版本。普通阅读不产生修改日志，真实写入、下载、导出和打印发起记录登录账号。

## 代码审查

审查对照固定基线及需求 v0.3，覆盖菜单和登录守卫、路由到 Service 的调用链、模型及四份 SQL、私有文件、事务边界、编辑会话、Markdown 保护、PDF 坐标和导出进程。未改变 plus 既有公开函数；档案仅由 Center 消费，edge/alert 不新增读路径。

审查与回归发现的问题已修复：

- MySQL 初始化唯一约束与 Gorm 名称不一致，修正后再次初始化和 AutoMigrate 通过。
- PDF.js 6 已移除旧矩形转换接口，改为两个端点转换，核对裁剪原点、旋转和 UserUnit；带批注导出独立解析验证坐标。
- 上传完成会覆盖打开表单的输入，改为固定打开时的信息及修订号；过期保存返回冲突。
- 图片仅凭头部不能判断完整性，增加受限尺寸后的完整解码，截断文件拒绝落正式版本。
- 历史 PDF 导出应依据所选版本的文件类型，不能依据已经替换后的当前附件类型。
- 历史阅读书签绑定所选版本；不合法编辑节点不能进入草稿或正式版本。
- 同一图片资产的多次使用需分别保留布局，Markdown 使用每处图片的独立引用，删除或移动后仍保留各自尺寸；新增回归从失败到通过。
- 慢速链路下，自动保存或模式切换中曾可点击正式保存但未执行。补齐可观察的等待状态，期间禁用保存、退出和模式切换；后台草稿保存仍允许继续输入正文。端到端回归延迟真实草稿请求，验证按钮等待后正式保存生成新版本。

## 验收入口与实际边界

使用 `https://n9e-dev2.zhiteng.win/archives`，沿用此开发预览的登录账号。先检查四个 Tab 及字段，再新建档案，上传资料或编写在线文档，保存、刷新续写、切换双模式、归档并修改，最后查看历史和人员日志。Word 转在线先检查转换结果；PDF 可添加批注并下载带批注文件。用第二窗口验证同一文档无法同时编辑。

Word 验收采用用户已确认的内容完整与系统内输出一致标准；复杂对象在 Markdown 中保持只读。当前格式样本及自动限额测试不等于任意复杂 Word、全部 50 MiB 文件的性能承诺。打印已覆盖生成内容与发起记录，操作系统实际打印仍由人工确认。客户部署需要固定 Node 24、LibreOffice、中文字体及许可声明，并同时备份数据库和私有文件目录，详见[运行说明](../../api/archives.md)。
